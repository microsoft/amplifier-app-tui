# Approachable experience — development verification

Scope: the approved [experience plan](../APPROACHABLE-EXPERIENCE-PLAN.md), toward existing
DRAFT contracts. No kernel/upstream changes, personal-service writes, release publication
or global-configuration mutation. Existing local work remains intact. The daily development
link loads this checkout on relaunch, not into an already running conversation.

## Delivered behavior

- Shared dark/light/terminal-default/NO_COLOR palette, matching syntax treatments,
  edge-to-edge native content and compact idle composer. Light paint covers the owned
  live region. Semantic labels remain useful without colour.
- Task-grouped Actions with global search and legacy aliases. Current-task correction
  is labelled Change task; queue management remains separate and deliberate.
- Bounded ordinary tool/public-progress/usage projections retain exact source in
  inspection. Notice metadata and mode observations remain structured; errors and
  unknown tool outcomes are not turned into task-success claims.
- Short menus retain reachable choices and scroll every detail line without skipped
  pages. Main drafts and locally selected question answers survive shrinking to 32×12.
- Current mode is observed at the provider-request boundary, with a transition-specific
  revision. Returning to default cannot deduplicate back to a reminder that precedes
  an older Explore state. This informs the model, never grants permission or alters
  module enforcement. Module-owned ephemeral persistence is retained, not bypassed.
- Current first-use documentation replaces the mixed historical front page; the original
  walkthrough is preserved separately. A scoped account/service verification procedure
  separates transport, indexing, memory injection, authentication and cleanup authority.
- Reusable actual-PTY journey driver, viewport/theme/question matrix, sustained two-preset
  live journey, process-tree resource observations and local-control timing instrumentation.

## Measured responsiveness, not a parity badge

Timing runs were serial and separate from this wave's builds, suites, captures and live
traffic. The shared machine was not reserved against unrelated workloads. Linux ARM64,
warm installed/source/OS caches, real PTY observation; scheduling and observer parsing
remain in the measurement. No global cache purge or cold-cache claim.

Thirty alternating configured TUI/CLI fixture pairs:

| Observation | TUI median / p95, ms | CLI median / p95, ms |
|---|---:|---:|
| Runtime startup to ready | 601.9 / 792.1 | 441.0 / 495.2 |
| Submit to first visible reply | 246.7 / 268.3 | 429.1 / 629.4 |
| Submit to final visible reply | 349.1 / 373.0 | 429.9 / 630.2 |

These are **non-equivalent policies**: the TUI startup is slower in this workload and
its visible fixture reply arrives sooner, but neither fact establishes default-product
speedup or non-regression. Prepared differences remain `tools.count` and the skills
configuration fingerprint; actual packaged skills assets match in all 21 files, while
their installed absolute path differs. The question schema and app recipe/mode request
guidance are genuine differences. No hooks or capabilities were removed to improve a score.

## Failures retained, not overwritten

The first whole run passed 578 and failed five checks: three wrap-sensitive expectations,
an outdated help phrase, and a selection-frame race. Focused corrected checks pass.
The second passed 591 and failed one simulated scrollback test: the explicit scrollback
status replaced Completed after the response had finished. Its assertion now checks
complete response content, Send availability and retained unsent text rather than a
particular transient status phrase. Earlier XML receipts remain separate.

Initial live attempts exposed two observer races around separate edit prompts; waiting
for their actual disappearance fixed them. Subsequent live work exposed real stale mode
guidance after clear. A simple repeated state observation was insufficient because the
streaming loop deduplicated it. The new default → explore → default ordered-request
regression failed before transition revisions and passes after them on both presets.
Failed live receipts remain private and separate from final success evidence.

An intermediate mode fix assumed a root-only sequence field and failed in a delegated
child. A standalone transition revision removes that assumption; the 54-test ecosystem/
control subset and both final live journeys pass. Clean installation exposed two further
verification issues: dependency development-source conflict (resolved with documented
`--no-sources`, pins unchanged) and the old Doctor "not imported" expectation (updated
to its actual read-only diagnostic boundary). No existing release was overwritten.

## Visual findings and boundaries

Primary reference is 175×50 total rows, not 45 rows plus arbitrary chrome. Developer
inspection includes primary, wide-short and narrow work views, light/dark menus, failed
test output and mode permission. Source starts at column zero; screenshot-renderer
pixel margins are not terminal gutters. Narrow code wraps and some secondary titles
truncate; full source and essential controls remain reachable. At 32×12, decisions take
the available screen and detail requires paging: safe navigation, not comfortable work.
The inspection view retains denser technical chrome than ordinary conversation.

Inspected private captures include the same daily fixture before/after at 175×50;
responsive work/questions and light/dark Actions; both live presets' delegation, mode
permission, failed/passing test, decision brief, resumed draft, review and child-wait
views. The ordinary answer is visually separate from its bounded tool evidence. A child
question shows its origin and an answer action while retaining the main composer.
At narrow widths, full child identities and secondary titles can wrap/truncate in the
preview; inspection retains exact identities. Full permission/request wording may need
paging at the minimum size. These are listed comfort limits, not hidden successful
desktop/mobile equivalence claims.
Opaque result objects from some recipe/delegation operations still use a bounded JSON
preview. Their status/target and full inspection path remain visible, but those previews
are less approachable than plain-language tool output; no arbitrary-result semantic
normalization is claimed. The ordinary assistant answer and its code remain separate.

Real tmux selection/exit retention is a separate gate from pyte screenshots. Physical
mobile keyboards, desktop font comfort, screen readers and remote OS clipboard behavior
are not certified by terminal-grid simulation. No native history is cleared or rewritten
to improve appearance. Earlier platform CI applies only to its published revision.

## Limits that remain explicit

Default CLI parity is not established: question schemas and app-owned request guidance
differ. Packaged skills config differs by install path even though all 21 asset bytes
match. Warm fixture timings cannot establish live/cold-policy equivalence.
The memory/HTTP gates use owned storage and loopback transport, not personal service
indexing or real account authorization. Follow [the separate procedure](../../docs/SERVICE-VERIFICATION.md)
with destination/account/cleanup authority before those actions. Publication requires
an identified release decision; no existing release is replaced by this checkout work.
